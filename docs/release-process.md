# Release process

SPDX-License-Identifier: MIT-0

Releases publish source and reproducibility evidence; they do not deploy AWS resources.
There is intentionally no automatic deployment or release workflow in version 1.

## Version policy

The initial public reference release is `v0.1.0`. The Python project metadata uses
`0.1.0`; Git tags add the conventional `v` prefix. Use semantic versioning as a
communication tool:

- Patch: compatible corrections and documentation improvements.
- Minor: compatible workflow features or schema support.
- Major: incompatible input, configuration, or operational behavior.

Do not reuse or silently move a published tag. Correct a release with a new patch
version and describe the superseded behavior.

## Release gate

Before creating a tag:

1. Refresh `docs/research-notes.md` against primary documentation.
2. Resolve or explicitly defer open dependency and security alerts.
3. Confirm `main` uses the protection in `docs/github-repository-settings.md`.
4. Run `make check` in a clean supported environment.
5. Run both local demos and inspect their sanitized output.
6. Run `make package` twice from clean build directories and compare SHA-256 output.
7. Confirm the worktree is clean and the exact release commit is on `origin/main`.
8. Confirm no state, plans, `.tfvars`, credentials, build directories, or ZIP files are
   tracked.
9. Prepare version-specific release notes and review them against the final diff.

## Manual publication

The maintainer performs these actions only after the reviewed change is merged:

```bash
git switch main
git pull --ff-only
make check
VERSION=v0.1.1 # Replace with the reviewed next version.
git tag -a "$VERSION" -m "aws-security-hub-workflow $VERSION"
git push origin "$VERSION"
```

Create a GitHub Release from that tag, use the prepared release notes, and mark it as a
pre-release if the workflow has not been exercised in an authorized AWS sandbox. Source
archives generated by GitHub are sufficient. If the Lambda ZIP is attached, attach its
`.sha256` file, state that it targets Linux arm64/Python 3.13, and rebuild it from the
tag rather than uploading an older local artifact.

## Post-release verification

- Confirm the release tag resolves to the reviewed commit.
- Confirm GitHub displays MIT-0.
- Confirm CodeQL and Scorecard remain enabled.
- Re-run the source quick start in a fresh clone without AWS credentials.
- Record the release URL and checksums in the audit report.

Do not create an AWS deployment to validate release publication. Any later AWS sandbox
validation is a separate, explicitly approved activity with its own plan and cleanup.
